# RefundDesk pilot threat model

> Scope: v1.1 pilot in local and approved AWS persistent hosting, Stripe test mode and managed sandbox
> Review date: 2026-08-08 (previous 2026-08-03)
> Re-review triggers: live-mode proposal, new payment method, Connect, new notification channel, new hosting topology or a financial/security incident
>
> The "new notification channel" trigger fired with ADR 0021 and had not been honoured: the
> outbound destination is a server-side request forgery primitive against the hosted network and
> no threat covered it. T23 covers the inbound direction — a generic Stripe proxy — not this one.
> T38 was added for it, and the residual-risk section corrected for the notification channel and
> for the key-rotation drills completed on 3 August. ADR 0034's independent-review result and
> read-only current-host postflight add the evidence-provenance threat covered by T39.

## 1. Security objectives

1. A Refund is created only for the intended tenant, environment, payment, amount and approved request.
2. A request creates at most one linked financial effect.
3. A requester cannot approve their own request or forge another Stripe user.
4. Cross-tenant reads and writes fail closed.
5. An ambiguous Stripe outcome cannot silently release the execution guard.
6. Secrets and sensitive workflow text remain confidential.
7. Audit history is attributable, append-only and retained for its stated period.
8. External or replayed refunds are detected without automatically creating another refund.
9. Live mode is unreachable in the authorized pilot.

This model does not claim PCI, SOC 2, ISO 27001 or regulatory certification.

## 2. Assets

Highest impact:

- separate Stripe platform read and worker effect credentials;
- the worker-owned Stripe App signing secret and approval-attestation HMAC key;
- webhook signing secrets;
- field-encryption and proof-HMAC keys;
- authority to create a Refund;
- tenant/environment binding;
- deterministic Stripe idempotency key;
- first linked Refund ID and effect state.

Sensitive:

- justifications and rejection reasons;
- approver membership and decisions;
- audit records;
- database credentials;
- migration-owner credentials and hosted secret configuration;
- mutation receipts and reconciliation state.
- durable signed-request rate-limit state.

Operational:

- Stripe Event and Refund identifiers;
- logs and metrics;
- scanner checkpoints;
- redacted phase-0 evidence.
- encrypted versioned PostgreSQL backups and their offline recovery identity;
- immutable GitHub/AWS release provenance and exact Stripe App version evidence.

RefundDesk does not need card PAN, CVC, customer e-mail, address or complete Stripe payload storage.

## 3. Actors

- Requester: authenticated Stripe Dashboard user who can view the payment.
- Approver: observed Stripe user explicitly enabled in RefundDesk.
- Administrator: can install/configure the app, but is not automatically an approver.
- Operator: maintains the local pilot and performs documented recovery.
- GitHub Actions: builds exact test/sandbox artifacts for the configured repository.
- AWS: hosts the approved test/sandbox runtime, versioned backups and disposable restore verifier.
- Stripe: identity, UI context, Refund API, events and sandbox provider.
- External integration: any other key/app able to create a Refund.
- Attacker: unauthenticated network actor, compromised Dashboard user, compromised runtime, malicious tenant user or database-only intruder.

## 4. Trust boundaries

```text
Stripe Dashboard UI
  -> signed app request boundary
RefundDesk web API
  -> exact raw-body forwarding + private service-authentication boundary
RefundDesk worker signature authority
  -> append-only approval-attestation + forced-RLS boundary
PostgreSQL

Verified signed envelope in RefundDesk web
  -> global pre-tenant SECURITY DEFINER GCRA boundary
PostgreSQL signed-request rate-limit state
  -> normal tenant dispatch and forced-RLS boundary
PostgreSQL tenant state

RefundDesk worker
  -> credential/account/environment boundary
Stripe Refund API

Stripe webhook sender
  -> raw-body signature boundary
RefundDesk webhook ingress

Operator
  -> secret store and migration role boundary
Local/runtime environment

Source + lockfile
  -> Linux OCI build boundary
Web / worker / one-shot migrator images

Hosting control plane
  -> service-specific secret injection boundary
Web, worker and serialized migrator

Versioned backup object
  -> out-of-band digest + offline age-identity boundary
Disposable PostgreSQL restore verifier

Committed repository HEAD
  -> pinned read-only AWS/SSH postflight boundary
Short-lived redacted local host-state evidence
```

Data crossing a boundary is untrusted until its authentication, schema, tenant and environment checks succeed.

## 5. Assumptions and exclusions

- Stripe’s signature and webhook primitives are correctly implemented by official libraries.
- The workstation and local secret storage are under the user’s control.
- Test and managed-sandbox credentials are distinct.
- Hosted web read keys and worker effect keys are distinct; real read-key denial and account binding
  passed separately in test and managed sandbox.
- The worker verifier endpoint is private to web-to-worker traffic; its bearer token authenticates
  the service but cannot replace a valid Stripe signature.
- Only synthetic data is used.
- A Dashboard user or external API credential with native refund rights can bypass RefundDesk; detection is the control.
- Denial of Stripe itself and compromise of Stripe infrastructure are outside the implementation threat model.
- A host postflight is a point-in-time containment observation. It is not a complete release,
  Compose-configuration, availability or CloudFront-origin admission.

## 8. Abuse cases exercised in Phase 0

All cases below contributed to the final `34/34 passed_real` evidence verdict.

1. Change one signed byte, reorder one field and substitute the account.
2. Use `View only` to attempt a native Stripe refund and a RefundDesk request.
3. Replay the same app request nonce with both identical and changed content.
4. Replay the Stripe refund call with the identical idempotency key.
5. Create a manual Refund without proof metadata.
6. Copy proof metadata to a second Refund.
7. Present test credentials to a managed sandbox installation and vice versa.
8. Present any `livemode=true` context.

## 9. Incident priorities

Severity 0:

- live effect during the pilot;
- duplicate Refund attributable to RefundDesk;
- Refund on the wrong account/payment/environment;
- exposed Stripe or cryptographic key;
- confirmed cross-tenant access.

Severity 1:

- ambiguous effect with guard intact;
- webhook and scanner both unavailable;
- audit integrity failure;
- sensitive workflow text in logs.

For response procedures, see `docs/OPERATIONS_RUNBOOK.md`.

## 10. Residual-risk acceptance

The pilot explicitly accepts:

- RefundDesk cannot prevent native/external refunds;
- a compromised authorized approver can approve another user’s malicious request;
- detection can exceed thirty minutes during Stripe or worker outage;
- local operator credentials are a high-trust boundary;
- the approved GitHub/AWS control planes and local/offline key stores are high-trust boundaries;
- hosted backup and real disposable restores are proven separately for `42a1e4e...`,
  `71bbd98...`, `4521b8c9...` and historical exact-e4; evidence does not transfer to changed
  source and the scheduled restore cadence still requires proof;
- primary maintenance failure remains a failed gate even when independent recovery restores
  availability; an unrecovered durable journal deliberately blocks release and maintenance;
- external alert delivery has a selected channel but no runtime: ADR 0021 chose an outbound HTTPS
  notification to a merchant-named destination, its policy and delivery client are built and unit
  tested, and the connection is pinned to the checked addresses (ADR 0027). Nothing sends today —
  the provider has no caller, no destination is stored anywhere, and the storage question belongs
  to ADR 0020. Treat T38 as stated but unexercised against a live socket;
- edge limiting, source filtering and two-stage
  attestation are implemented and locally tested but are not claimed as hosted until exact-revision
  CloudFront/Caddy traversal and a real Stripe source pass. The durable post-signature GCRA has
  exact PostgreSQL CI evidence but no changed-revision hosted signed-route proof;
- the committed-HEAD read-only host postflight is admissible and returned `FAIL` with posture
  `COHERENT_RUNNING`. At `2026-08-08T12:37:17Z` it observed active `8da280b7...`, five healthy
  services, worker/Caddy/maintenance and internal TCP 80/443 listeners active, two unexpected
  running containers (`unexpectedRunningContainerCount=2`) and a runtime quiescence journal. The
  AWS 80/443 firewall was closed and unchanged,
  live was disabled and the financial state was stable/quiescent. Exact diagnostics were
  `CADDY_RUNNING`, `MAINTENANCE_ACTIVE`, `PUBLIC_LISTENER_ACTIVE`,
  `UNEXPECTED_RUNNING_CONTAINER`, `UNRESOLVED_JOURNAL` and `WORKER_RUNNING`. The evidence expired
